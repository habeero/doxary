# Domain data model

## Entities and relationships

The confirmed browsing hierarchy is `Organization 1--* Case 1--* Document 1--* DocumentFile`. A newly imported Document is nevertheless valid without an Organization or Case: `Document.organization_id` and `Document.case_id` are initially absent. A Document has zero or more analyses, tasks, deadlines, appointments, amounts, required documents, and conversations. Case-level views aggregate related document facts without changing their source document. A task may be manual or analysis-suggested and can link to one document or case.

All entities have opaque stable IDs, `created_at`, `updated_at`, provenance (`user`, `analysis`, or `system`), and optional source-analysis/version references. The local Document ID is specifically `client_document_id`, generated by the client and used to correlate AI results. User corrections take precedence over suggestions while retaining optional provenance for explainability. `operation_id`, `request_id`, and future `server_resource_id` are API/infrastructure identifiers, not substitutes for the local domain ID.

| Entity | Key fields | Lifecycle |
|---|---|---|
| Organization | name, normalized_name, category, contact hints | active, archived |
| Case | organization_id, title, status, opened/closed dates | active, completed, archived |
| Document | client_document_id, organization_id?, case_id?, classification_state, type, received/document dates, status, source language | imported, processing, analyzed, needs-review, archived, deleted |
| DocumentFile | client_document_id, local URI, media type, stable file ID, original filename/size, import source, ordered page index, timestamps | local, temporary-processing, unavailable, deleted |
| ExtractedText | client_document_id, text, page/range, extraction confidence | available, partial, unavailable |
| DocumentAnalysis | client_document_id, schema/prompt versions, output language/style, typed extracted facts, separate explanation, quality reasons, typed source references, confidence | complete, partial, unavailable; versioned/history retained locally |
| Task | case_id?/client_document_id?, title, due date, status, reminder | open, completed, dismissed |
| Deadline / Appointment | source client_document_id, datetime/date range, timezone, confidence | active, completed/past, cancelled |
| Amount | value/currency, direction, due date, purpose | active, paid/received, uncertain |
| RequiredDocument | description, status, due date | requested, obtained, submitted, not-applicable |
| ConversationMessage | scope, role, localized content, citations | active, deleted |

Organization category is a configurable label, not business logic; initial labels include immigration authority, Jobcenter, Familienkasse, health insurer, tax office, employer, housing/landlord, and other.

## Import and classification lifecycle

On import, the client creates and saves a Document with `classification_state: unclassified`; both relationship IDs are absent. Analysis may add an `organization_suggestion` and `case_suggestion`, changing the state to `suggested`, but suggestions live with analysis/provenance and are not copied into confirmed IDs. The user may accept, edit, or reject suggestions. Only accepted or manually entered relationships set `organization_id` and `case_id` and produce `classification_state: confirmed`; if `case_id` is set, its organization must equal `organization_id`. Classification failure leaves the Document saved and analyzable as `unclassified`; no misleading “Unknown” Organization or Case is created.

The Documents tab presents the complete non-deleted local library; Home intentionally uses the bounded recent stream. User-facing titles derive from analyzed document type/date (optionally with the confirmed organization), then a genuinely meaningful cleaned filename, then a localized generic fallback—never an opaque ID. Opaque, generic, and date-only filenames are not titles.

## State and timestamps

Dates retain precision (`date` versus timestamp), source wording, inferred timezone where applicable, and an uncertainty indicator. Deadlines and appointments must retain their source excerpt/reference when available. Deleting a document deletes derived local items only after user confirmation or turns linked records into explicitly orphaned/manual records according to the future UX decision.

## Future sync

Maintain local deletion tombstones and `revision`/server-version fields only when sync is introduced. A future sync mapping may attach `server_resource_id` to a local `client_document_id`, without replacing the local identity or requiring server originals. Original file upload/storage needs separate, opt-in consent and lifecycle metadata; it is not implied by syncing analysis metadata.

## Phase 1 schema v1

Drift/SQLite schema v2 implements normalized tables for organizations, cases, ordered document files, analyses/history, typed quality reasons, source references, tasks, deadlines, appointments, amounts, required documents, and non-sensitive user settings. `documents.client_document_id` is the primary local identity; organization/case foreign keys are nullable. Original bytes remain outside SQLite.

Schema versions are never reset or treated as disposable. Schema v3 adds `analysis_operations`, a client-owned record of a pending backend `operation_id`, its local document correlation, public lifecycle state, and safe failure code. Schema v4 persists the typed organization suggestion and document type with each local analysis so review survives restart; they remain analysis provenance, never confirmed relationships. Successful results create a new local `Analyses` row and remove the pending operation; user-confirmed organization/case relationships are never touched.
